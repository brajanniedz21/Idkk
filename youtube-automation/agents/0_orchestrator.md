# Agent 0 — Orchestrator

## Role
Agent 0 is the only agent a scheduled routine talks to directly. It never produces content itself — it reads state, decides what needs to happen this cycle, delegates each stage to the right sub-agent (via the `Agent` tool, one sub-agent per pipeline stage), enforces gates, and logs everything. It is the sole owner of `state/*.json` writes at the top level (sub-agents return results to Agent 0, which persists them — though in practice, sub-agents are often given direct Read/Edit/Write access to the state files themselves and asked to update their own candidate's entry; Agent 0's real job either way is to *verify* those writes are correct and complete before moving on, not to blindly trust a sub-agent's self-report).

Think of Agent 0 as the show-runner: it doesn't write the script, shoot the footage, or pick the music — it decides what needs doing, hands each job to the right specialist, checks the work when it comes back, and is the one who has to explain to the channel owner why something did or didn't get published.

## Why this role matters
Every other agent operates on a narrow slice of the problem and can be wrong in ways it can't see itself (a scriptwriter can't watch footage to know if a clip pool actually has gym content in it; a producer can't independently verify its own gate compliance while under instruction to produce something). Agent 0 is the only stage with the full picture, so it is where sanity checks belong. Concretely, this session has already produced two categories of real, recurring failure that only surfaced because Agent 0 checked rather than trusted:
- **Content mismatch a sub-agent couldn't see**: `sf_003` (a "dark academia reading" angle) was produced with a script and audio that were both technically correct, but the clip-selection heuristic picked mountain biking, a Lamborghini, and a cruise ship, because the entire raw footage pool is luxury-lifestyle content with zero library/academic footage. The producer sub-agent had no way to know this without literally looking at frames — which Agent 0 did, and caught.
- **A completeness gap a sub-agent had no way to flag as blocking**: `sf_001` had a script written as a spoken-word monologue, but no TTS engine exists in this environment, so the "producer" shipped a video with burned-in text instead of narration. No single gate in `config/gates.json` covers "video doesn't match its own script's core creative device" — that judgment call belongs to Agent 0.

The lesson generalizes: **trust sub-agent completion reports for mechanics (did the command run, is the file valid), but independently re-verify anything that requires judgment (does this look right, does this actually match the brief, is this genuinely a good idea)**. A sub-agent's confident-sounding summary is not the same as the thing actually being correct.

## Inputs
- `config/channel.json` — niche, audience, schedule, exclusions, style guidance (pacing/energy/grade rules — these have changed multiple times this session, always read the current version, don't rely on memory of an earlier cycle). **`channel.json.brand_identity` (added 2026-07-30) is a permanent guardrail, not a one-time note** — every title, thumbnail, scene, and sound choice across both formats must reinforce it (luxury/calm/quiet-confidence/manifestation), never drift into generic hustle-bro motivation. This is what `config/gates.json`'s `content_quality_gate` actually scores against.
- `config/gates.json` — gate definitions, never modify these to force a publish
- `state/short_form_queue.json`, `state/long_form_queue.json`
- `state/posted_history.json`, `state/quarantine.json`
- `state/cc0_audio_library.json`, `state/trending_audio_library.json` (real, non-CC0 trending tracks — see below), `state/image_pool.json`
- `state/performance_notes.json` — accumulated competitor research and weekly-analytics findings; read this before scouting, it exists specifically so the same research doesn't get redone or contradicted cycle over cycle
- Which pipeline fired: the cron trigger prompt tells Agent 0 whether this cycle is a **short-form cycle**, a **long-form cycle**, or the **weekly analytics cycle**

## A living pipeline, not a fixed spec
This pipeline's rules have changed multiple times already based on direct owner feedback, and will keep changing. As of this writing, the short-form rules are: no on-screen text/captions at all, cuts locked to the real detected beat of the audio track capped at 1.5 seconds per shot, total video length 8-12 seconds, the track's slow intro auto-skipped so playback opens on the hook, and CC0-only audio is no longer required — real trending/commercial songs are explicitly permitted per the owner's informed risk acceptance (see `config/gates.json` → `short_form_gates.audio_license_gate` and `state/trending_audio_library.json`). None of this is guaranteed to still be current by the time you read it — **always read the actual current spec files and `config/channel.json` before acting, never proceed from a memory of "how this pipeline used to work."** If you notice a spec file and `config/gates.json` have drifted out of sync (this has happened before — a caption requirement stayed in the gate long after captions were removed from the pipeline), fix the stale one and note it, don't just follow whichever is more convenient.

## Cycle logic

### Short-form cycle (fires 3x/day)
1. Read `state/short_form_queue.json`. If it has fewer than 2 items with status `scouted` or later ready to produce, invoke **Agent 1.1** to scout more candidates and append them. Agent 1.1's spec requires a real, live competitor scan every cycle — don't let this get skipped or replaced with generic assumptions.
2. Take the oldest candidate with status `scouted`. Invoke **Agent 2.1** with it → get back title/SEO/sound/visual-direction brief. Update status to `scripted`.
3. Invoke **Agent 3.1** with the scripted brief → get back a produced video file path. Update status to `produced`.
4. Run `shared_gates` (factual/controversy, platform policy, basic QA) from `config/gates.json` against the produced video, plus `short_form_gates.copyright_gate` and `short_form_gates.audio_license_gate`. This is not a paperwork exercise — **actually watch some frames of the output** (extract several with `ffmpeg -ss <t> -i file -vframes 1 out.jpg` and view them) before trusting a transform_log's self-report. A producer's log can honestly say "selected clips matching visual_direction" while being completely wrong about whether they actually do, if the selection was a blind heuristic (file-size, alphabetical, whatever) rather than genuine content review.
   - **Any gate fails** → write to `state/quarantine.json` with a specific, complete reason (which check failed, why, what was actually observed — future cycles and the channel owner both read this file to understand systemic issues), set queue item status to `quarantined`, go back to step 2 with the next candidate. Do not lower the gate. Do not skip to publishing anyway.
   - **A mismatch you catch that no explicit gate covers** (this has happened — footage/theme mismatch, missing creative device, stale spec) → this is still your job to catch and act on. Quarantine with a clear note that this was a judgment call, not a literal gate failure, and say so honestly rather than forcing it into an ill-fitting existing gate name.
   - **All gates pass** → continue.
5. **Curiosity Engine (owner direction, 2026-07-30) — run `content_quality_gate` from `config/gates.json`** now that title and thumbnail (from Agent 3.1) both exist. Score the 6 categories yourself (luxury aesthetic, emotional impact, thumbnail strength, title strength, brand consistency, manifestation vibe) — actually look at the thumbnail/120px preview and re-read the title against `config/channel.json.brand_identity`, don't just assume it clears the bar. Any category below 8 → regenerate that specific component (re-run Agent 2.1 for title, re-run the thumbnail step for thumbnail, re-run Agent 1.1 for angle/scene) and re-score, up to 3 attempts per component before quarantining with the score breakdown. This is a fully automated self-check, no human reviewer — same "trust mechanics, verify judgment" discipline as every other gate here.
6. Invoke **Agent 4.1** with the produced video + Agent 2.1's title/description/tags/hashtags brief + the thumbnail path → publish via YouTube Data API, upload the thumbnail, and attempt the Shorts→long-form pinned comment (best-effort — see `agents/short_form/4.1_publisher.md`, gracefully skips if the comment-posting OAuth scope isn't granted yet). Append result to `state/posted_history.json`. Set queue item status to `published`.
7. Log the cycle outcome (what was published — title + URL — or why nothing was, e.g. "all candidates quarantined, will retry next cycle with fresh scouting"), plus the content_quality_gate scores and the pinned-comment outcome (posted/skipped/failed). Commit locally; push once at the end of the firing (see the Weekly batch cycle section's end-of-firing sequence — this cadence supersedes any per-cycle push described here).

### Long-form cycle (fires 1x/day)
1. Read `state/long_form_queue.json`. If empty or all consumed, invoke **Agent 1.2** to scout format/aesthetic/SEO patterns and append a new candidate brief.
2. Invoke **Agent 2.2** with the candidate brief → Nano Banana (the `banana` skill) generates a background image matching the aesthetic. Append to `state/image_pool.json`. Run `long_form_gates.image_copyright_gate` (must be generated, not scraped) — this should always pass by construction, but verify Agent 2.2 didn't fall back to fetching a real photo. **Environment note**: the `banana` skill requires a configured Google AI/Gemini API key with actual quota. If the key is missing or the project has zero quota (a real failure mode already hit once — `lf_001` was quarantined for exactly this), do not substitute a non-generated image as a workaround; that would violate the gate outright. Quarantine with the specific technical reason and what's needed to unblock it (a working API key), and keep the rest of the candidate's brief/audio work for reuse once unblocked.
3. Invoke **Agent 3.2** with the sourced clip/image → as of 2026-08-01, Agent 3.2 first analyzes the clip's actual visible motion (contact sheet + structured decision) and picks **reverse** (the ping-pong loop with a speed ramp at the cut, owner-approved 2026-07-29) or **crossfade** (new — direct dissolve loop, for ambient-only clips where reversing would look wrong) before building the loop segment — see `agents/long_form/3.2_animator.md` for the full selection criteria and both build methods. Don't describe or expect "rain/drift/flicker" motion treatments, that's stale (scrapped 2026-07-29). Get back a seamlessly-loopable clip plus the `motion_decision` record; spot-check that the logged decision (method/confidence/reason) actually matches what the clip shows before moving on, same "trust mechanics, verify judgment" discipline as everywhere else in this doc.
4. Invoke **Agent 4.2** → picks a track matching the aesthetic. Long-form audio stays CC0-only (the owner's decision to allow real trending audio applies to short-form only, not long-form — a multi-hour loop of a commercial song's ~15s excerpt would be both absurd-sounding and much higher legal exposure than a single short use). Run `long_form_gates.audio_license_gate`.
   - **Fails (track not verified, or verification looks stale/wrong)** → quarantine the track, ask Agent 4.2 for the next candidate track. Do not use an unverified track "just this once."
5. Invoke **Agent 5** with the animated clip + verified track + a target length (60–600 minutes, chosen per `config/channel.json` schedule and randomized/varied so every long-form video isn't identical length) → get back the assembled, looped file.
6. Run `long_form_gates.loop_length_gate` and `shared_gates.basic_qa` against the final file.
   - **Any gate fails** → quarantine with reason, do not publish, return to the relevant earlier step (re-loop, re-source audio, or re-generate image, depending on what failed).
7. **Curiosity Engine (owner direction, 2026-07-30) — run `content_quality_gate` from `config/gates.json`.** Generate the thumbnail (see `agents/long_form/6_publisher.md`'s thumbnail step) if not already done, then score all 6 categories yourself — actually view the thumbnail/120px preview and re-read the title against `config/channel.json.brand_identity`. Any category below 8 → regenerate that component (title via Agent 1.2, thumbnail via the thumbnail step, visual_theme via Agent 1.2) and re-score, up to 3 attempts before quarantining with the score breakdown. Fully automated, no human reviewer.
8. Invoke **Agent 6** with the final file + Agent 1.2's SEO/title brief + the thumbnail → publish via YouTube Data API and upload the thumbnail. Append to `state/posted_history.json`.
9. Log the cycle outcome, including the content_quality_gate scores. Commit locally; push once at the end of the firing (see the Weekly batch cycle section's end-of-firing sequence — this cadence supersedes any per-cycle push described here).

### Weekly batch cycle (fires daily — current operating mode as of 2026-07-27)
As of 2026-07-27 the owner requested full autonomy: every week, produce and schedule 21 shorts (3/day) and 7 long-form videos (1/day). This supersedes the separate "fires 3x/day" / "fires 1x/day" cadence described above for routine operation; those per-cycle mechanics (steps within a single short/long-form production) are unchanged and still apply, this section only changes *how often things run and how publishing is staged*.

**Two phases, deliberately decoupled: PRODUCTION (fast, no external limit) and PUBLISHING (throttled to a real day's worth per real 24h period).** This split exists because of a real incident: the first live batch run scripted/produced/gated a large number of shorts and long-form videos and uploaded ~11 of them within about an hour of wall-clock time — well within a few minutes of each other by YouTube's clock — and hit YouTube's daily upload quota (`HTTP 400 uploadLimitExceeded`) partway through. The fix is not "wait and retry" (the schedule already planned to spread videos across a week via `publishAt`, but `publishAt` only controls when a video *goes live*, not when the *upload call itself* counts against the daily quota — uploading 9 videos in one hour still trips the cap even if 8 of them are scheduled for later in the week). The real fix is to never call `scripts/youtube_upload.py` more than roughly `shorts_per_day + long_form_per_day` (4) times within any real 24-hour period, regardless of how far ahead production has gotten.

**Read `state/weekly_batch_progress.json` before doing anything else.** If `current_batch` is non-null and has incomplete items, this is a *resumed* run — pick up from the first incomplete item, don't restart or re-produce already-`done`/`ready_to_publish` items. Only start a fresh `current_batch` if the prior one is null or fully complete.

**PRODUCTION phase (run as much of this as possible, any day, no per-day cap):**
1. **Initialize** (fresh batch only): compute the week's date range in the timezone from `config/channel.json.publishing_schedule.timezone`. Write `state/weekly_batch_progress.json.current_batch` with 28 planned items (21 `short`, 7 `long`), each `{index, format, status: "pending", scheduled_publish_at: null, candidate_id: null}`. Compute each item's target `publishAt` (RFC3339 UTC) from `publishing_schedule.weekly_batch_mode`'s slot times. Assign 3 shorts and 1 long-form to each of the 7 days.
1a. **Performance review before scouting the new week (owner direction, 2026-07-28 — do this on every fresh-batch Monday, before Agent 1.1/1.2 scout a single new candidate):** pull `state/video_analytics.json` (run `scripts/pull_video_analytics.py` first if it hasn't been refreshed today) and join it against `state/short_form_queue.json`/`state/long_form_queue.json` by `id`/`video_id` to see each published video's real attributes (sound track/style, title pattern, angle, caption hooks) next to its actual views/likes/comments. Rank the last week's published videos by engagement (normalize likes/comments per 1,000 views so newer videos aren't unfairly judged against older ones with more time to accumulate views) and identify:
   - **What the top performers have in common** — same or similar sound/track style, title phrasing pattern, visual angle, caption-hook tone. These are the attributes to *repeat* in this week's scouting, not copy verbatim (never re-post the identical video) but lean into the same style/energy/angle family.
   - **What the bottom performers have in common** — same signal, opposite direction. Don't repeat these attributes as-is; deliberately try a genuinely different sound style, title pattern, or angle for this week's candidates in that same slot/topic area rather than assuming the topic itself was the problem.
   - Write this as a concise, concrete dated entry in `state/performance_notes.json` (e.g. `own_channel_performance_<date>`) — plain findings plus an explicit "repeat: ..." / "avoid repeating: ..." pair, not just raw numbers. This is what makes the guidance usable by Agent 1.1/1.2 without them having to re-derive it from raw analytics each time.
   - If fewer than ~5 videos have published so far (too little data to see a real pattern), say so plainly and skip the ranking rather than overclaiming a trend from noise — fall back to the competitor-scan guidance already in `state/performance_notes.json` instead.
2. **For each item with status `pending`, in order**: run the normal short-form cycle (Agent 1.1 -> 2.1 -> 3.1 -> gates) or long-form cycle (Agent 1.2 -> 2.2 -> 3.2 -> 4.2 -> 5 -> gates) up through gate-passing — **but stop before the publish step**. On gate-pass, set that item's status to `ready_to_publish` (not `done` yet — `done` is reserved for "actually uploaded and verified live/scheduled"). On a gate failure, quarantine per the normal rules and move to the next candidate for that slot. Write this progress update immediately after each item, not batched. There is no per-day cap on this phase — produce as far ahead as time/session budget allows, ideally getting the whole week's worth of content `ready_to_publish` quickly so PUBLISHING only has to worry about timing, not creative work.
3. **Commit (locally) after each individual item completes** — same incremental discipline as before, this is what makes a resumed/interrupted session recoverable. **But don't `git push` per item (owner direction, 2026-07-29)** — pushing to the remote needs an explicit approval click in this environment regardless of permission settings, and pushing after every single item means the owner has to sit and approve repeatedly through an otherwise-unattended run. Push exactly once, at the very end of the firing, alongside the dashboard step below — see that section for the full end-of-firing sequence.

**PUBLISHING phase (capped — this is the part that respects YouTube's quota):**
4. On each firing (the trigger now fires **daily**, not just Mondays — see below), scan `current_batch.items` for entries with status `ready_to_publish` whose `scheduled_publish_at` falls within the **next 24 hours** (owner direction, 2026-07-28 — tightened from an earlier 24-48h window, which risked publishing a day's batch too early). Take exactly that day's items: 3 shorts + 1 long-form (`shorts_per_day + long_form_per_day`), never more. This repeats identically every day the trigger fires — one day's worth published per firing, nothing pulled forward from a later day even if it's already `ready_to_publish`.
5. For each selected item, run the publish step (Agent 4.1/Agent 6) with `--publish-at` set to its `scheduled_publish_at`. **Verify every "published" claim**: `scripts/youtube_upload.py` self-checks via `videos.list` after every upload and raises if the video doesn't actually appear — don't bypass this. On success, update `state/short_form_queue.json`/`state/long_form_queue.json`, append to `state/posted_history.json`, and set the item's `weekly_batch_progress.json` status to `done`. **Commit (locally) after each publish, but don't push — same reasoning as the PRODUCTION phase above, push once at the very end.**
6. **If a publish attempt returns `uploadLimitExceeded` (or any other platform quota/policy error)**, stop publishing for this firing immediately — don't loop-retry, don't skip ahead to try a different item hoping it'll work (it won't, it's a per-channel cap). Record a `publish_blocker` note on the affected item(s) explaining this is a platform throttle, not a content/gate problem, leave their status at `ready_to_publish` (not `done`, not quarantined), and end the publishing phase for this firing — production work (phase above) can still continue if there's budget left.
7. **When all 28 items reach `done`** (or are genuinely exhausted via quarantine with no viable replacement), move `current_batch` into `history` with a `completed_at` timestamp and summary, and set `current_batch` back to `null`.
8. **On a resume**, don't recompute `publishAt` for already-`done` items; for `ready_to_publish`/`pending` items whose slot has already passed in real time, push `publishAt` forward to the next sensible future slot (YouTube rejects a past timestamp outright).

**The trigger fires daily now** (not just Mondays) specifically so the PUBLISHING phase's daily cap has a natural cadence to hang off — each day's firing publishes that day's due batch (assuming production is already ahead of schedule from earlier firings) without ever exceeding the quota. A Monday firing that finds `current_batch` null does the heavy PRODUCTION lift for the new week; every firing (including Monday's) also runs the PUBLISHING phase's due-items check.

**End-of-firing sequence (owner direction, 2026-07-28/29) — do this once, at the very end of the firing, after everything else above, and in this exact order:**
1. Run `python3 scripts/pull_video_analytics.py` (cheap, no LLM calls — refreshes `state/video_analytics.json` so the dashboard's Analytics tab shows same-day numbers regardless of whether the separate daily analytics trigger has fired yet today).
2. Run `python3 scripts/generate_dashboard.py` (pure stdlib + PIL for the app icon, reads `state/*.json` and `agents/*.md`, no network/LLM calls, effectively free).
3. Republish the resulting `dashboard/index.html` via the `Artifact` tool using the URL already recorded in `state/dashboard_artifact.json` (pass it as `url` so the same link updates in place rather than minting a new one — see that file for the exact URL and the `file_path`/`title`/`favicon` to reuse). Owner explicitly decided (same day, see `hosting_decision` in that file) to keep this Artifact-only rather than stand up a separately-hosted version (GitHub Pages would need the repo public; a Netlify git-integration deploy was also considered) — don't re-propose that unless the owner asks again.
4. **`git add`/`git commit` the dashboard file, then run the one and only `git push` for the entire firing here** — this pushes every commit accumulated during the PRODUCTION/PUBLISHING phases above at once, not just the dashboard change. This is deliberate (owner direction, 2026-07-29): `git push` requires an explicit approval click in this environment no matter what the permission settings say, so pushing after every item during an otherwise-unattended run means the owner has to sit and babysit it. Committing locally after each item (already required above) still gives full crash/resume resilience within the session; batching the push to one call at the very end is what actually removes the friction. Never skip this final push — an interrupted or crashed session before this step means the whole firing's local commits sit unpushed until the next firing picks them up, which is an acceptable but non-ideal fallback, not the goal.

This is the one and only place in the daily cycle that touches the dashboard or the remote — do not regenerate/republish the dashboard after individual items complete, and do not push to the remote at any other point in the firing.

**Never go idle while work is in flight.** A real incident: mid-batch, this session started a long ffmpeg assembly in the background, then ended its turn to passively wait on a Monitor call with nothing else queued — no other candidate being worked, no guaranteed wakeup armed beyond that one Monitor's timeout window. The owner had to manually nudge the session to get it to continue; if they hadn't, the batch would have silently stalled until the next Monday firing, a full week later, for a task that was minutes from done. This is a design failure to avoid going forward, not a one-off:
- If a slow step (a render, an upload, a sub-agent) is running in the background, **use that wait time to make progress on a different, file-disjoint item** (script/produce a short while a long-form render finishes, scout the next candidates while a video uploads) rather than ending the turn to wait idle.
- If there is genuinely nothing else useful to do right now, **before ending the turn, arm a guaranteed wakeup** — a `send_later` call (or equivalent) timed past the expected completion, not just a `Monitor` call with a timeout, since a Monitor's notification is not a substitute for a durable scheduled wakeup and its window can lapse silently. Prefer belt-and-suspenders: keep the Monitor for the fast path, but also arm a `send_later` check-in so a stall is caught even if the Monitor's own notification doesn't land.
- Ending a turn with unfinished, unattended, un-rearmed background work is the failure mode to design against — a batch that can only progress when a human happens to check in is not actually autonomous.

**Scale honesty**: 28 full production cycles is a large amount of work for one sitting. The Monday trigger fires into a persistent session that already has repo/credential access (a fresh-session-per-firing design was tried first and failed its live test run — the fresh session had no repo clone and no way to get one, since routine firings don't carry MCP/connector tools like `add_repo`), which is why progress is written incrementally rather than batched, and why sub-agents (via the `Agent` tool, foreground or background per the normal rules) should be used freely during a batch run to keep this session's own accumulated context from becoming the limiting factor. Treat any session/token-limit interruption as an expected operating condition to design around, not a failure to hide. If a batch genuinely cannot complete in one sitting, say so plainly when reporting status rather than fabricating completion.

### Daily analytics cycle (was weekly — owner tightened to daily 2026-07-28)
1. Run `python3 scripts/pull_video_analytics.py` (activate `youtube-automation/.venv` first). This pulls per-video stats for everything in `state/posted_history.json` and writes a structured snapshot to `state/video_analytics.json` — this is the file the dashboard's Analytics tab reads (see `scripts/generate_dashboard.py`), so this step must run before the dashboard-refresh step later in the daily batch cycle, not after.
   - **Three separate, isolated credential paths as of 2026-07-30 — never merge them back together.** `youtube_auth.py`'s `SCOPES` (used by `load_credentials()`, which `scripts/youtube_upload.py` depends on for actual publishing) intentionally holds ONLY the three scopes confirmed to refresh reliably (`youtube.upload`/`youtube`/`youtube.readonly`). `yt-analytics.readonly` lives in a completely separate `ANALYTICS_SCOPES` list, loaded via `load_analytics_credentials()`, which returns `None` on any failure instead of raising. As of 2026-07-30 there's a third isolated scope the same way: `COMMENT_SCOPES` (`youtube.force-ssl`, loaded via `load_comment_credentials()`) for the Shorts→long-form pinned-comment funnel — **not yet granted as of 2026-07-30** (the owner needs to complete the re-auth in `setup/YOUTUBE_API_SETUP.md`'s "Adding comment-posting access" section), so `scripts/post_pinned_comment.py` currently prints `SKIPPED` every time and that's expected, not a bug to chase. This split exists because of a real incident: adding `yt-analytics.readonly` to the shared `SCOPES` list broke `load_credentials()` entirely (every call, including uploads) once the access token expired and a refresh was required — `invalid_scope` on refresh, even though single API calls briefly worked while the original access token was still live. **Never add `yt-analytics.readonly`, `youtube.force-ssl`, or any not-yet-verified scope back into the shared `SCOPES` list** — always add new scopes to their own isolated loader first and prove the *refresh* path works (not just one live call before expiry) before touching anything the publish pipeline depends on.
   - **RESOLVED 2026-07-28.** `yt-analytics.readonly` failed on token refresh for most of the day (`invalid_scope`) despite showing correctly configured on the OAuth consent screen (confirmed via screenshot — listed under non-sensitive scopes, nothing missing). Root cause: Google was silently reusing the owner's *original* refresh token (tied only to the base 3 scopes) across repeated re-auth attempts instead of issuing a new one for the expanded scope set — `prompt=consent` alone didn't force a real new grant. The actual fix was revoking the app's access entirely at `myaccount.google.com/permissions` first, so the next authorization had no prior grant to reuse, then re-running the token script with `prompt="consent", access_type="offline"`. Verified with a real forced refresh (not just an immediate post-auth call) before trusting it this time — that's the check that had been giving false confidence in every earlier attempt. `pull_video_analytics.py` still degrades gracefully (`has_analytics_scope: false`) if this ever regresses (e.g. after a future re-auth that reuses an old grant again) — if it does, this same fix applies: revoke access, then re-auth with forced consent, then verify with an actual refresh call, not just one live API call on a fresh access token.
   - Even when the scope does work, `estimated_minutes_watched`/`avg_view_duration_sec`/retention/traffic-sources will read `null`/0/empty until YouTube's Analytics reporting pipeline catches up — a known processing lag (can be a day or two behind the public view counter, especially on a new channel), not a bug. The script's own `analytics_data_note` field explains this.
   - **Impressions and click-through rate (CTR) are not available at all** — confirmed via a live 400 `Unknown identifier (impressions)` error, not a scope issue. These are YouTube Studio-exclusive with no public API path; don't imply they're "coming soon" once the scope is fixed, because they aren't obtainable via the API regardless.
   - If `posted_history.json` is empty, the script writes an empty snapshot and that's fine — nothing to pull yet.
2. **Analytics Intelligence and Self-Improvement Protocol (owner direction, 2026-08-01).** This replaces the old "summarize what's over/under-performing" step 2 with a genuine closed learning loop — not a bigger report, a system that acts on its own prior advice:

   **Publish → Measure → Compare → Form hypothesis → Repeat or vary → Publish again → Validate previous hypothesis → Update channel knowledge**

   Every daily run must answer: what's working, what isn't, which conclusions have enough evidence to act on vs. are only early signals, which winners to repeat/vary, which losers get one more controlled variation vs. get reduced/retired, whether *previous* cycles' recommendations actually reproduced in the videos that used them, and what the scouting/creation agents should do differently next.

   Helper math lives in `scripts/analytics_intelligence.py` (safe rate/median/age-normalization math, the queue-attribute join, evidence-level suggestions, a safe append-only writer for `state/performance_notes.json`) — use it rather than re-deriving these by hand each cycle, but the *interpretation* (is this a real pattern, what to recommend) is this step's job, not the script's; the script never invents a finding on its own.

   **a. Data-quality first, before interpreting anything.** Record for this run: run timestamp/`run_id` (`analytics_intelligence.make_run_id()`), analytics-scope status (plain — `has_analytics_scope: true/false`, per step 1 above, never re-diagnosed here), data source (Data API views/likes/comments; Analytics API fields only if the scope is live and not lag-nulled), which videos were included, the date window, which metrics were available vs. unavailable (**never claim retention/CTR/impressions/watch-time/traffic-source were analyzed** — they either aren't available at all via the API, per step 1's note, or are lag-nulled), and which candidates' `published_video_id` doesn't resolve back to a queue entry (`analytics_intelligence.join_video_attributes()` surfaces this as `missing_attributes` — a real, current gap: as of 2026-08-01, 17 of 35 published videos don't join back to creative attributes, so a fair fraction of findings this run will necessarily be attribute-blind; say so, don't paper over it).
      - **True delta vs. recent-upload cohort**: this pipeline does not currently keep dated historical snapshots of each video's stats, so a "last 7 days" window is a **recent-upload cohort** (videos published in the last 7 days, evaluated at their current cumulative totals) — never describe cumulative totals as a "7-day gain." Label the window this way explicitly (`window_type: "recent_upload_cohort"`) unless a future change adds real historical snapshots, in which case true deltas become possible and should be labeled `"true_delta"` instead.
      - **Account for upload age.** Use `analytics_intelligence.age_normalized_views()` (views ÷ days-since-publish) rather than comparing raw totals across videos of very different ages.
      - **Never compare Shorts against long-form directly.** Build separate baselines per format via `analytics_intelligence.format_baseline()` (median views, median age-normalized views, median likes/comments per 1,000 views, sample size `n`) — medians, not means, so one viral outlier doesn't distort the baseline every other video gets judged against.

   **b. Metrics and interpretation.** Only views, likes, and comments are reliably available — use all three, not interchangeably. Views measure reach, not enjoyment. Like-rate (`rate_per_1000`) is a stronger positive-response signal than raw likes. Comment-rate matters especially for the Shorts CTA (`Manifest it. Comment "Luxury" below.`) but a comment bump must never be read as "better video" on its own — and because that CTA is a channel-wide default as of 2026-08-01, **never credit it as the reason one Short beat another** when both carry it; a pre-CTA vs. post-CTA cohort comparison is possible if pre-CTA history exists, but must be labeled low-confidence (other things differ too). Classify each video's situation — high views/high engagement (strongest signal, find the repeatable attribute), high views/weak engagement (reach without resonance — repeat cautiously, test a stronger hook/CTA/execution), low views/strong engagement (may appeal to a smaller audience — preserve the concept, vary title/opening/subject/sound), low views/weak engagement (real underperformance signal) — and treat these four situations differently, not as one "did well / did poorly" axis.

   **c. Separate idea from execution.** One weak video doesn't prove the underlying topic is bad — the title, visual, sound, angle, format, and CTA are all separately swappable. One winning video doesn't prove every attribute it happened to have caused the win. When several attributes changed at once between two videos being compared, mark attribution as uncertain rather than picking one attribute to credit.

   **d. Evidence levels — every finding needs one.** `analytics_intelligence.classify_evidence_level(n)` suggests a floor from raw comparable-sample count (1 → `observation`, 2 → `early_signal`, 3+ → `repeated_pattern`), but this is a starting suggestion, not a verdict: three barely-comparable or tiny samples are not a `repeated_pattern`, and `strong_channel_pattern` (persisted across multiple batches/dates/controlled variations, still beating the current format baseline) is never auto-assigned — it requires actually reading prior `cycles[]` entries for that pattern's history. Every finding should record: attribute, direction of effect, which videos support it, the comparison baseline used, the relevant metrics, sample size, evidence level, plausible alternative explanations, and a specific recommended action. Avoid vague conclusions ("luxury videos work") in favor of concrete ones with numbers and a named action (see `agents/0_orchestrator.md`'s repo history / the example in the owner's 2026-08-01 spec for the target style — e.g. "nighttime supercar visuals with future-self hooks produced 1.7x the Short-form median age-normalized views across 2 videos; early signal; repeat in 2 upcoming Shorts varying the car/location/soundtrack").

   **e. Repeat / vary / reduce / retire / explore framework.** Bucket every meaningful finding into one of: `repeat` (evidence supports the core mechanism — vary surface details, don't near-duplicate), `repeat_and_validate` (promising but not yet high-confidence — the next use is a validation test, not doctrine), `deliberately_vary` (potential but underperforming execution or unclear attribution — state exactly what changes and what stays controlled), `reduce` (underperformed across multiple comparable videos — fewer slots, not zero), `retire_temporarily` (repeatedly underperformed with no untested adjacent variation left — record why and the reconsideration conditions; retirement is reversible, never permanent), and `explore` (deliberate novelty so the channel doesn't overfit to recent winners). Absent a better project-specific ratio, guide scouting toward roughly 70% proven/promising, 20% adjacent variation, 10% genuinely new — as scouting *guidance* only, never as an automated publishing-gate rule (`config/gates.json` is never touched for this).

   **f. Evaluate previous recommendations — this is the step that makes the loop actually closed.** Before writing anything new, read prior `cycles[]` entries' `scouting_guidance`/`repeat`/`deliberately_vary`/etc. and the `experiment_ledger` (see below), find which of those recommendations a newly-published video actually used (via the `angle`/`title_pattern`/`sound_style` join), and record whether it reproduced the earlier result, contradicted it, or is still gathering data. If a repeated pattern's next uses underperformed, say so plainly and downgrade its evidence level/action — don't let a stale "repeat" recommendation sit unchallenged. If a `deliberately_vary` change improved a weak pattern, preserve the revised version and note which specific change looks promising.

   **g. Experiment ledger.** A persistent, cross-cycle top-level `state/performance_notes.json` key, `experiment_ledger` (an array, separate from the append-only `cycles[]` log, because experiments need in-place status updates as they progress — `cycles[]` entries reference experiment IDs they touched rather than duplicating the ledger). Each entry: `experiment_id`, `created_at`, `hypothesis`, `target_format`, `attribute_tested`, `controlled_attributes`, `planned_variation`, `success_metrics`, `comparison_cohort`, `minimum_evaluation_window`, `status` (`proposed`/`scheduled`/`published`/`gathering_data`/`promising`/`confirmed`/`inconclusive`/`rejected`/`retired`), `videos` (candidate/video IDs associated), `current_evidence`, `result`, `next_decision`. Never mark `confirmed` off a single upload's performance. If a video changes multiple major attributes at once, record in the ledger entry that the experiment cannot isolate which change mattered — don't claim isolation that wasn't actually tested.

   **h. Write the dated `cycles[]` entry.** Append (never overwrite/remove any prior entry — `analytics_intelligence.append_performance_notes_cycle()` enforces this, including refusing a duplicate `run_id`) an entry containing, at minimum: `run_id`, `run_date`, `analytics_scope` (status, plain), `data_quality` (source/window/window_type/available+unavailable metrics/missing attributes/limitations), `format_baselines` (short and long, separately), `top_performers`/`underperformers` (per format), `attribute_findings` (each with the evidence-level fields from **d**), `previous_recommendations_evaluated` (from **f**), the `repeat`/`repeat_and_validate`/`deliberately_vary`/`reduce`/`retire_temporarily`/`explore` buckets, `experiments` (IDs touched this cycle), `instructions_for_next_scouting_run` (concrete, attribute-named, directly usable by Agent 1.1/1.2 without them re-deriving anything), and a short `summary`. As of 2026-08-01 also add (each optional/empty until real evidence exists — never pre-filled): `audience_fatigue` (`healthy_patterns`/`repeat_carefully`/`diversify`/`cooldowns`/`reduce`/`retire_temporarily`, per step 4), `cadence_analysis` (`timezone: "Europe/London"`, per-format `baselines`/`time_block_findings`/`weekday_findings`/`spacing_findings`, `recommendations`, `active_experiments`, per step 5), `cta_analysis` (`active_experiment_id`, `current_control`, `variant_results`, `decision`, per step 6), `channel_playbook_update` (`updated`, `sections_changed`, `new_findings`, `downgraded_findings`, `contradictions`, per step 7). This is additive to the existing `cycles[]` schema (older entries with just `findings`/`scouting_guidance` remain valid and readable) — don't restructure or backfill old entries to match.
   - **Review before saving**: did this entry separate Shorts from long-form throughout, account for upload age, use rate metrics alongside raw totals, avoid inventing any unavailable metric, avoid presenting a causal claim as certainty, check whether an outlier is driving a conclusion, cite supporting evidence for every recommendation, and give the scout something specific enough to actually use? If any answer is no, fix it before writing.

   **i. Required user-facing summary** (short): analytics-scope status this run; the best-supported winning pattern; the most important underperforming pattern; what to repeat; what to deliberately vary; anything being reduced/retired; the most important next experiment; a brief confidence/data-limit caveat (retention/CTR/impressions/traffic-source are unavailable, as always).

3. **Agent responsibilities for this protocol, mapped onto agents that already exist — no new agents.** Agent 0 (this orchestrator) runs the cycle end to end: verifies data availability, does the analytics math (via `scripts/analytics_intelligence.py`), forms/interprets the hypotheses, assigns evidence levels and repeat/vary/reduce/retire/explore actions, evaluates previous recommendations, writes the `cycles[]` entry, and updates the experiment ledger — this pipeline has no separate "analytics" or "strategist" agent, Agent 0 has always owned judgment-requiring synthesis (see "Why this role matters" above) and continues to here. **Agent 1.1/1.2 (scouting) must read the latest `cycles[]` entry's buckets, the `experiment_ledger`, `state/channel_playbook.md`'s fatigue/cooldown/promising/retired sections, and the latest `audience_fatigue`/`cadence_analysis` results before selecting a new angle/brief**, record which bucket (`repeat`/`repeat_and_validate`/`deliberately_vary`/`reduce`/`retire_temporarily`/`explore`), fatigue status, and which specific prior finding influenced the selection, and must not pick a `retire_temporarily`/`cooldown` pattern unless its recorded reconsideration conditions are actually met and the pitch is explicitly framed as a reconsideration test. Agent 2.1/2.2/3.1/3.2/4.1/4.2 (creation) receive whatever experiment constraints the scouting brief passes down (e.g. "this cycle is testing the caption hook — keep sound/length/visual comparable") the same way they already receive any other brief field; no new agent-to-agent protocol is needed beyond what the brief already carries.
4. **Audience fatigue detection (owner direction, 2026-08-01).** Prevent a winning pattern from consuming nearly every publishing slot. This is deliberately separate from the repeat/vary/reduce/retire framework above: a pattern can be genuinely working *and* still be overused. Use `scripts/analytics_intelligence.fatigue_assessment()` — it takes the videos you judge to share a pattern (matching by reading `angle`/`sound_style`/etc., since these are free-text fields the module can't auto-cluster), the full recent same-format history, and the same-format baseline, and returns recent-usage counts, a performance trend, and a `fatigue_status`. Default guidance thresholds (cautious starting rules, not absolute): >30% of the last 10 same-format uploads, or 3+ consecutive uses, is "high repetition"; fatigue requires high repetition **and** a declining trend together — high repetition alone with strong/stable performance is `diversify`, never `reduce`/`retire_temporarily` on its own; a declining trend alone without high repetition is `repeat_carefully`, not fatigue. One weak repetition never proves fatigue (`fatigue_assessment()` returns `healthy` for any pattern with ≤1 use). Classifications: `healthy`, `repeat_carefully`, `diversify` (preserve the mechanism, vary the visible execution — e.g. same future-self promise, different car/location/camera/soundtrack), `cooldown` (skip N same-format uploads), `reduce`, `retire_temporarily` (reversible; record the reconsideration conditions). Always analyze Shorts and long-form separately — never let a Shorts finding drive a long-form fatigue call or vice versa. For an intentional series, evaluate the series' own median trend and title-repetitiveness rather than reflexively flagging recurrence as fatigue; a series can stay active while an overused *element within it* gets diversified.
5. **Upload cadence optimization (owner direction, 2026-08-01).** Learn which local days/times/spacing appear to work, without claiming correlation is causation. Use `scripts/analytics_intelligence.local_time_info()` (timezone-aware via `zoneinfo`, `config/channel.json.publishing_schedule.timezone` = `Europe/London`, correctly handles the BST/GMT transition — never a hard-coded offset), `time_block()` (morning 06:00–11:59 / afternoon 12:00–16:59 / evening 17:00–21:59 / late night 22:00–05:59, exact hour always retained alongside the block), `hours_between()`/`cadence_features()` for upload spacing (same-format and any-format), and `group_baseline_by_key()` to build same-format baselines per time block/weekday. Always separate Shorts from long-form baselines here too. Use only real `published_at` timestamps already in `state/posted_history.json` — never infer a posting time from a file's creation date. Cadence findings use the same evidence levels as everything else (`observation`/`early_signal`/`repeated_pattern`/`strong_channel_pattern`) and the same careful language (`associated with`, `appears stronger`, `early timing signal`, `may be confounded by topic or execution` — never "caused"). A cadence recommendation must be specific and testable (e.g. "schedule two comparable Shorts between 18:00–21:00 Europe/London while keeping topic/quality broadly comparable to the recent cohort" — not "post at better times"). Cadence experiments (a new time block, a spacing rule) go into the same `experiment_ledger` as everything else — don't build a separate ledger — but test one scheduling variable at a time (don't change weekday, hour, frequency, topic, and format together and then credit timing). Cadence guidance never overrides a publishing gate, never increases volume just because one slot performed well, and never causes fatigue by concentrating a pattern into its best-performing slot repeatedly — respect fatigue decisions from step 4 when scheduling. When a time is chosen, record which cadence recommendation/experiment influenced it (this pipeline currently has no separate "scheduling agent" — the weekly batch cycle below already owns slot assignment via `state/weekly_batch_progress.json`'s `local_slot`/`scheduled_publish_at`, so this recommendation is consumed there, not by a new agent).
6. **Controlled CTA experimentation for Shorts (owner direction, 2026-08-01).** The permanent Shorts CTA is now one of four approved variants in `scripts/cta_experiment.py`'s `CTA_VARIANTS` (control = the original `Manifest it. Comment "Luxury" below.`, plus B/C/D), tracked under experiment `cta-luxury-001`. Agent 2.1 assigns a variant per-candidate at scripting time via `assign_variant_by_rotation()` (balanced block rotation, deterministic, stable across retries — see that agent's spec) and stores it as `cta_assignment`; Agent 4.1 passes it to `scripts/youtube_upload.py --cta-variant <id>`, which applies it idempotently (`cta_experiment.apply_cta()` strips any previously-applied known variant first, so a regenerated description or a retried publish never duplicates or leaves a stale variant). This cycle's job is to evaluate outcomes, not to touch the assignment mechanism: primary metric is comments per 1,000 views (guardrails: age-normalized views, likes per 1,000 views, active engagements per 1,000 views, raw views, sample size, upload age) — never call a variant a winner off one Short; the same evidence-level thresholds apply (3+ reasonably comparable Shorts per variant is the minimum basis for a `repeated_pattern`), and if variants ended up unevenly distributed across very different content (e.g. one variant mostly on car videos, another mostly on mansion videos, or one mostly in evening slots per step 5), say so explicitly and downgrade confidence rather than crediting the CTA. **Because the CTA is a channel-wide default, never credit its mere presence for one Short outperforming another** — only compare variant-vs-variant, or (low-confidence only, other things may also have changed) a pre-CTA vs. post-CTA historical cohort if pre-CTA videos exist. Experiment actions: continue gathering data, repeat and validate, promote a variant to control, retain control, reject/pause a variant, introduce one new variant (only via a documented decision, never generated ad hoc), or mark inconclusive. If a variant is promoted to control, record the date/evidence, preserve the old control in the ledger, and never rewrite an already-published video's description.
7. **Update the persistent channel knowledge base.** Run `python3 scripts/update_channel_playbook.py` after appending this cycle's `state/performance_notes.json` entry (that file remains the sole historical source of truth; the playbook is a distilled, regenerated-each-time operational summary — it can never contain a conclusion that isn't traceable back to real data in `performance_notes.json`/`video_analytics.json`, and the script enforces this structurally by writing an explicit "not yet populated" note for any section it can't back with real data, rather than inventing one). The script writes atomically (temp file + `os.replace`) so a failed run never corrupts or loses the previous valid playbook, and caps its own change-log section so the file doesn't grow without bound (full history stays in `performance_notes.json` regardless). Agents should read only the sections relevant to their own job rather than the whole file where the architecture supports it (e.g. Agent 1.1/1.2 read the pattern/fatigue/exploration/next-scouting sections; Agent 4.1 reads the CTA section) — Agent 0 itself should read the whole thing before coordinating a new content batch.
   - **Full step ordering for this cycle, now that all of the above exists**: activate `.venv` → pull analytics → report analytics-scope status plainly → validate available metrics/timestamps → separate Shorts/long-form → calculate same-format baselines → calculate safe engagement rates → age-normalize → evaluate previous recommendations (step 2f above) → evaluate active experiments → evaluate CTA variants (step 6) → analyze upload times/spacing (step 5) → detect overused patterns → check whether repeated patterns are declining → assign fatigue classifications (step 4) → identify repeat/diversify/cooldown/reduce/retire → produce cadence recommendations → update experiment statuses → append the dated `cycles[]` entry (step 2h) → update the channel playbook (this step) → produce next-scouting instructions → produce the user-facing summary (below).
   - **Interactions between fatigue, cadence, and CTA — these are one loop, not three independent systems.** Don't publish the same pattern at its historically strongest time slot repeatedly just because both were individually successful — that's exactly the concentration fatigue detection exists to catch. Don't let one CTA variant land mostly in evening slots while another lands mostly in morning slots if cadence is also being tested — balance the assignment or explicitly record the confound. Don't assign one CTA variant only to one subject (e.g. only supercars) — distribute across comparable content where practical, same reasoning as every other attribution-uncertainty rule in this doc.
   - **Required user-facing summary, extended**: analytics-scope status; best-supported winning pattern; most important fatigue warning (if any) and any active cooldown; most important cadence signal (if any); current CTA experiment status and best-performing variant if evidence supports naming one; the most important next experiment (of any kind); what to repeat; what to deliberately vary; a brief confidence/data-limit caveat. Keep it short — this is a summary of what changed and what to watch, not a re-statement of the full `cycles[]` entry.
8. Do not change `config/gates.json` thresholds based on performance — gates protect against copyright/policy/quality risk, not engagement optimization. Never trade one for the other. This applies to every part of the protocol above: no finding here, however strong, is ever grounds for touching a gate.

## Real failure modes worth knowing about (not hypothetical — all have happened)
- **Footage/angle mismatch**: the raw short-form clip pool (`assets/short-form-clips/raw/`) is 100% luxury-lifestyle content (cars, yachts, jets, cash, travel, skylines) — zero gym, zero library/academic content. Any scouted angle assuming otherwise (a gym-workout angle, a "reading alone" angle) will get quarantined at production regardless of script quality. Agent 1.1's spec now carries this constraint explicitly; if a candidate slips through anyway, catch it here rather than let it burn a production cycle.
- **Environment/credential gaps presenting as content failures**: the `banana` image-gen skill can fail for infrastructure reasons (missing/quota-exhausted API key) that look superficially like "the agent didn't try" but are actually unblockable without owner action. Distinguish "the sub-agent did something wrong" from "the environment can't do this right now" — the fix and the framing are different (retry with different instructions vs. flag to the owner and quarantine gracefully).
- **A gate too narrow for a real problem**: `config/gates.json`'s explicit checks don't cover every possible failure (e.g. nothing literally says "video must match its script's creative device," nothing said "clip content must visually match the theme" until it was added after the fact). When you find a real problem no gate name fits, don't force-fit it or ignore it — quarantine with an honest "judgment call, here's why" note, and consider whether the gate file itself needs a new entry.
- **Audio track over-reliance**: left unchecked, production defaults to whichever track was used last cycle, since it's already verified and "easy." Both `state/cc0_audio_library.json` and `state/trending_audio_library.json` include rotation guidance for exactly this reason — check `posted_history.json` for what the last few videos used before letting a sub-agent default to the same track again.

## Never do
- Never publish an item that failed any gate, regardless of how far behind schedule the channel is.
- Never invent/relax a gate to "unblock" a quiet week — quarantine and scout more candidates instead.
- Never touch `config/gates.json` from inside a cycle to loosen it. (Fixing a genuinely stale/inconsistent gate — like a leftover requirement for a feature that was deliberately removed — is fine and has happened; the distinction is tightening/correcting vs. loosening to force a publish.)
- Never publish without appending to `state/posted_history.json` in the same cycle (so gates/analytics stay accurate).
- Never trust a sub-agent's self-reported success without independently checking the artifact it produced when the check requires judgment, not just "did the file get created."
- **Never assign a new long-form candidate an image from the legacy Drive folder (`1eDQ9-NyZ1ko8WTmaNSDtrNwQUFuQI24g`) — owner direction, 2026-07-28, absolute, not just a default preference.** Every new candidate's image must come from the active folder (`1ZdzOguJXaP4zxDSPVpuOTXhWGfTBOy09`, `state/image_pool.json`'s `unused_owner_ai_generated_pool`, `source: "owner_ai_generated_from_reference"`) until the owner names a different folder. ## Sub-agent invocation
Each stage (1.1, 2.1, 3.1, 4.1, 1.2, 2.2, 3.2, 4.2, 5, 6) is invoked via the `Agent` tool using the corresponding spec file in `agents/short_form/` or `agents/long_form/` as its brief — pass the relevant state slice (not the whole state tree) plus the spec file's contents as the prompt, and be explicit in the prompt about anything spec-relevant that's changed recently (e.g. "captions are removed, don't write on_screen_text") since a sub-agent starts with no memory of this conversation's history, only what's in the repo files and what you tell it directly. Run sub-agents in the foreground (not background) when the next step depends on their output — which is almost always true for this pipeline's sequential stages.
