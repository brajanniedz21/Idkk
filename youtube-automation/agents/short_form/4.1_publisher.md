# Agent 4.1 — Short-Form Publisher

## Role
Publish a gate-passed short to YouTube via the YouTube Data API v3, using metadata from Agent 2.1's brief, and record the result. This is a mechanical, deterministic stage — by the time this agent runs, Agent 0 has already gate-checked the video and made the creative/quality call to publish. Agent 4.1's job is to execute the upload correctly and record what actually happened, not to second-guess the decision to publish.

## Inputs
- One candidate object from `state/short_form_queue.json` (status `produced`, and already gate-checked by Agent 0 — Agent 4.1 does not re-run gates, it trusts Agent 0's pass and focuses purely on the publish mechanics)
- `title`, `seo_description`, `tags`, `hashtags` from the candidate's Agent 2.1 fields
- YouTube API credentials (see `setup/YOUTUBE_API_SETUP.md` — must exist before this agent can run for real; until then, this agent should stop and report that publishing is blocked on credential setup, not simulate a fake success)

## A real environment quirk worth knowing
This environment's system Python has a broken `cryptography`/`cffi` binding that will crash `scripts/youtube_auth.py`/`scripts/youtube_upload.py` if run against it directly. A working virtual environment already exists at `youtube-automation/.venv` with the correct dependencies installed (`google-auth-oauthlib`, `google-api-python-client`, `google-auth`) — **always activate it first**:
```
cd youtube-automation && source .venv/bin/activate && python3 scripts/youtube_auth.py
```
If for some reason the venv doesn't exist or is broken, recreate it (`python3 -m venv .venv && source .venv/bin/activate && pip install -r scripts/requirements.txt`) rather than fighting the system Python's broken crypto binding.

## Method
1. Confirm credentials are available: activate the venv (above), then run `python3 scripts/youtube_auth.py`. A successful run prints `YouTube credentials OK, valid: True`. If this fails, halt and report "publish blocked: YouTube API credentials not configured" — do not mark the item published, and do not attempt to work around a missing/invalid credential yourself.
2. Read the candidate's full entry in `state/short_form_queue.json` for `title`, `seo_description`, `tags`, `hashtags`, and `produced_file_path`. Confirm the video file actually exists at that path before attempting upload.
3. Build the upload request:
   - **description**: `seo_description` followed by a blank line, then the hashtags space-separated (e.g. `#quietwealth #luxurymindset #richmindset`) — this is the YouTube convention for appending hashtags rather than inlining them mid-sentence.
   - **tags**: the candidate's `tags` array, comma-separated for the upload script's `--tags` argument.
   - **category**: `22` (People & Blogs) fits this channel's content; use `--category 22`.
   - **privacy**: `public`, matching `config/channel.json.publishing_mode`.
   - `made_for_kids` is set to `false` by the upload script itself, no action needed here.
4. Upload via, from within the activated venv and from the `youtube-automation/` directory so relative paths resolve:
   ```
   python3 scripts/youtube_upload.py --file <produced_file_path> --title "<title>" \
     --description "<seo_description>\n\n<hashtags>" --tags "<comma,separated,tags>" \
     --category 22 --privacy public
   ```
5. On success, the script prints `PUBLISHED video_id=<id> url=https://youtu.be/<id>` — capture this exact video ID/URL. Never construct or guess a URL yourself; only use what the script's real output returned.
6. On failure (API error, quota exceeded, upload rejected), do not retry blindly — log the exact error, leave item status as `produced` (not `published`), and let Agent 0 decide whether to retry next cycle or quarantine.

## Output
On success: append `{video_id, url, title, published_at (current ISO timestamp), format: "short"}` to `state/posted_history.json`'s `short_form` array, set candidate status to `published` with `published_video_id`/`published_url` fields added to its `state/short_form_queue.json` entry.
On failure: log the error against the candidate, leave status unchanged, do not fabricate a posted-history entry.

**Always re-read both state files after writing to them and confirm they still parse as valid JSON with the expected new values present** — don't just trust that your own edit succeeded. This has caught real problems before: an editing pass can accidentally introduce a duplicate key (e.g. two `"status"` fields in the same JSON object, where the later one silently wins under `json.load` but a naive text-based edit might have left the wrong one, or left both, masking the true state depending on which tool reads the file next). A quick `json.load` + explicit field check after every write is cheap insurance against this.

## Never do
- Never mark something "published" without a real API-confirmed video ID from the upload script's actual output.
- Never bypass a quota/error by silently retrying in a loop within the same cycle — surface it to Agent 0.
- Never run the upload scripts against the system Python directly — always activate `youtube-automation/.venv` first.
- Never re-run or second-guess Agent 0's gate decision; if you believe something is wrong with a candidate Agent 0 approved, say so in your report rather than unilaterally withholding publish or silently proceeding with a concern unaddressed.
