## 1. What this is

A fully autonomous, no-human-approval content pipeline that scouts, scripts, produces, gates, and publishes real videos to a live YouTube channel: **`@makeitmanifest`** ("Make it Manifest" — motivational luxury/manifestation faceless content). Real channel, real uploads, real audience. Not a simulation or a staging environment.

- **Repo**: `/home/user/Idkk` (git), working subpath `/home/user/Idkk/youtube-automation`.
- **Branch**: `claude/youtube-automation-agents-ifqozb` — all work happens here.
- **Niche**: motivational luxury background/ambience videos (`config/channel.json.niche`).
- **Format mix**: 70% short-form (YouTube Shorts, 8-12s), 30% long-form (60-600 min ambient loops).
- **As of this writing**: 39 real videos published (31 short, 8 long), 23 subscribers, 10,865 lifetime views (`state/channel_stats.json`). `publishing_mode: public`, `human_approval: disabled` (`config/channel.json`).

## 3. Core operating model: the Weekly batch cycle (restored 2026-08-03)

**History**: the original "Weekly batch cycle" (produce a full week ahead, throttle only publishing) was replaced on 2026-08-02 by a daily-only model (produce+publish only today's items) to make a real quota incident structurally impossible. On 2026-08-03 the owner explicitly asked to go back to producing/scheduling a full week at once ("usage credits are higher now" — session/compute budget, a different resource from YouTube's own API quota). The weekly model is restored, in `agents/0_orchestrator.md`'s "Weekly batch cycle" section:

- **PRODUCTION phase** (no daily cap): script/produce/gate the full week's items (21 shorts + 7 long-form) ahead of schedule, stopping at `ready_to_publish` — never actually uploading yet.
- **PUBLISHING phase** (throttled, real quota awareness): uploads each `ready_to_publish` item with `privacyStatus=private` + `publishAt` set to its real scheduled time, so it actually goes live on the right day — but checks for `uploadLimitExceeded` after every single upload and **stops immediately, no retry**, the instant it occurs (a real 2026-07-27 incident: ~11 uploads in an hour tripped this, even with `publishAt` already spread across the week — the upload *call* is throttled, not just the public time). Remaining items stay `ready_to_publish` for the next firing.
- `state/weekly_batch_progress.json` is the week-ahead production queue again (28 items, `pending` → `ready_to_publish` → `done`/`quarantined`).
- This is orthogonal to the Growth Strategy's production-*allocation* decision (§5b below, `config/growth_strategy.json.current_production_allocation`) — that still governs shorts/long-form *counts* per day; this section only changed *when* production/publishing happen relative to each other.

Two scheduled triggers drive this (external to the repo — see §9):
1. **Daily content batch** (~06:00 UTC) — runs the production cycle above.
2. **Daily analytics cycle** (~07:00 UTC) — runs the Self-Improvement Protocol below.

## 4. The Analytics Intelligence & Self-Improvement Protocol

Also in `agents/0_orchestrator.md`, this is the most complex part of the system. Full step list is in the doc; summary:

1. Pull real data: `scripts/pull_video_analytics.py` (views/likes/comments), `scripts/pull_channel_stats.py` (subscriber/lifetime totals), `scripts/pull_video_comments.py` (real comment text, organic vs. automated).
2. Build same-format baselines (medians, never means — one viral outlier shouldn't set the bar). **Never compare Shorts to long-form directly.**
3. Assign an **evidence level** to every finding: `observation` (n=1) → `early_signal` (n=2) → `repeated_pattern` (n=3+) → `strong_channel_pattern` (never auto-assigned, requires cross-cycle persistence, human-style judgment call).
4. Bucket findings: `repeat` / `repeat_and_validate` / `deliberately_vary` / `reduce` / `retire_temporarily` / `explore` (~70/20/10 repeat/vary/explore guidance).
5. **Evaluate whether previous cycles' recommendations actually reproduced** — this is what closes the loop. Read prior `cycles[]` entries, find which new videos used that recommendation, check if it worked.
6. Maintain `state/performance_notes.json.experiment_ledger` (persistent, in-place-updated array — separate from the append-only `cycles[]` log).
7. **Audience fatigue detection** (`scripts/analytics_intelligence.fatigue_assessment()`): >30% of last-10 same-format uploads or 3+ consecutive = high repetition; fatigue requires high repetition **and** a declining trend together. High repetition alone with strong performance → `diversify`, never `reduce`.
8. **Cadence optimization**: timezone-aware (`Europe/London`, DST-correct via `zoneinfo`), per-format baselines by weekday/hour/time-block/spacing.
9. **CTA experimentation** (see §6).
10. Regenerate `state/channel_playbook.md` (`scripts/update_channel_playbook.py`) — a distilled, always-current summary that can never contain an unbacked claim (script enforces this structurally).

**Absolute constraints, repeated throughout the doc because they've been violated by looser instructions before:**
- Never fabricate retention, CTR, or impressions — CTR/impressions have **no API path at all**, ever (confirmed via a live 400 error, not a scope issue). Retention/watch-time exist but lag-null for new uploads.
- Never touch `config/gates.json` based on performance findings — gates protect against copyright/policy/quality risk, not engagement optimization.
- `state/performance_notes.json` is **append-only** for `cycles[]` — never edit or remove a prior entry. Use `scripts/analytics_intelligence.append_performance_notes_cycle()`, which enforces this and refuses duplicate `run_id`s.

## 5b. Growth objective and controlled self-modification (added 2026-08-02)

The owner set an explicit growth objective: **100,000 subscribers by 2027-04-21** (a stretch objective, not a forecast). `config/growth_strategy.json` holds the adaptive policy (checkpoints, production-allocation models A-E, evidence-to-change-risk mapping, breakout/quota thresholds, rollback policy) — separate from `channel.json` (static brand identity) and never duplicating `gates.json` (safety). `scripts/analytics_intelligence.calculate_trajectory()` computes real GREEN/AMBER/RED status from a real per-day subscriber series (`pull_video_analytics.py` now pulls `subscribersGained`/`subscribersLost` with `dimensions="day"`) — never fabricated; on a brand-new channel `data_confidence` will honestly read `low`/`very_low`/`no_data` for a while.

**The pipeline is explicitly allowed — and required — to modify itself** (agents, scripts, config, schedules, production allocation, Routine prompts) when evidence supports it, following the "Controlled Self-Modification Loop" in `agents/0_orchestrator.md`'s "Growth Strategy" section: observe → diagnose → hypothesize → define the change → record baseline → implement → test → verify → activate → observe the evaluation window → decide (`keep`/`keep_and_expand`/`continue_testing`/`revise`/`rollback`/`inconclusive`) → record. Changes are classified low/medium/high risk with matching evidence requirements (`early_signal` / `repeated_pattern` / `strong_channel_pattern`) — **no new agent role is ever created for this**, Agent 0 remains the sole strategic authority. The safety rules in §8 of this doc all override the growth objective, always.

First real cycle (2026-08-02): trajectory came back `RED` (honest — 5 real days of data, ~2.8 subs/day vs. ~385/day required). Dominant constraint candidate: Shorts reach ~20x further than long-form so far, but classified only `early_signal` (not `repeated_pattern`) given the format-discovery confound and the total absence of per-video subscriber-attribution data anywhere in the API — no allocation change was made; "insufficient evidence, retain current model" is treated as a legitimate outcome, not a failure to act.

## 6. Systems built this session (all real, all live-tested)

- **Subscribe animation overlay** — branded overlay baked into short-form output.
- **Loop-selector for long-form** — `scripts/loop_contact_sheet.py` + `scripts/motion_decision.py` + `scripts/loop_builder.py`: analyzes motion in a sourced clip, picks `crossfade` or `reverse` (ping-pong) looping automatically, verifies no ghosting at the blend frame before accepting.
- **CTA experimentation** (`scripts/cta_experiment.py`) — 4 variants under experiment `cta-luxury-001`, deterministic balanced rotation (`assign_variant_by_rotation`), assigned at script time by Agent 2.1, applied idempotently by `youtube_upload.py --cta-variant <id>`. **CTA is the description's FIRST line** (changed 2026-08-02 from last-line — Shorts only shows the first line in its collapsed preview; `strip_known_cta()` checks leading line first, trailing as backward-compat fallback).
- **Pinned-comment Shorts→long-form funnel** (`scripts/post_pinned_comment.py`) — posts on every published Short. Text is now a **fixed line, no link**: `"Manifest with ambience, full videos on my channel."` (owner direction 2026-08-02 — an earlier version auto-linked to the most recent long-form video; owner asked for the fixed line instead). Graceful-degradation by design: prints `SKIPPED` if the comment scope isn't available, never blocks a publish.
- **Clip-reuse cooldown** (`scripts/clip_pool_status.py`) — real owner-caught bug: `raw/68.mp4`/`raw/65.mp4` reused across 3 published Shorts in a row because the old anti-repeat rule was just prose an agent had to remember. Now: structured `clips_used` field per candidate, `recently_used_clips()` computes a real last-5-published cooldown set, `agents/short_form/3.1_producer.md` requires running it before selecting clips (hard block, not a preference).
- **Dashboard** (`scripts/generate_dashboard.py` → `dashboard/index.html`) — fully rebuilt this session with a verified-contrast OKLCH color system, no glassmorphism/bounce animation (see `impeccable` skill's anti-slop guidance), 5-tab bottom nav, mobile-first. Published as a Claude Artifact — **always republish to the existing URL** stored in `state/dashboard_artifact.json`, never mint a new one.
- **Composio YouTube integration** — the owner has a Composio connection to the same channel. It's the same Data API v3 surface the pipeline's own credentials already use (no retention/CTR access beyond what's already impossible). Useful for ad-hoc live inspection during a session; not wired into the automated pipeline (the pipeline uses its own isolated OAuth credentials, see §7).

## 7. OAuth credential architecture — DO NOT MERGE THESE

`scripts/youtube_auth.py` has **three deliberately isolated credential paths**. This split exists because of a real incident: adding `yt-analytics.readonly` to the base `SCOPES` list once broke `load_credentials()` entirely (every call, including uploads) when a token refresh was required.

| Function | Scopes | Used by | Status |
|---|---|---|---|
| `load_credentials()` | `youtube.upload`, `youtube`, `youtube.readonly` | `youtube_upload.py` (actual publishing) | Always required — **never add another scope to this list** |
| `load_analytics_credentials()` | `yt-analytics.readonly` | `pull_video_analytics.py` | Returns `None` on failure, never raises. Has flipped between working/not working before — always report the actual `has_analytics_scope` value from the current run, never assume last time's status holds |
| `load_comment_credentials()` | `youtube.force-ssl` | `post_pinned_comment.py`, `pull_video_comments.py` | **Confirmed working as of 2026-08-02** (real pinned comments posted successfully) |

**Rule, stated explicitly because it's been the source of a real production incident**: any new scope goes into its own isolated loader first, and must be proven to survive an actual token *refresh* (not just one live call on a fresh access token) before it goes anywhere near `SCOPES`.

## 8. Hard rules — read before generating any change

- **Never touch `config/gates.json`** based on performance/engagement findings. Gates are copyright/policy/quality risk controls, period.
- **Never modify `SCOPES` in `scripts/youtube_auth.py`** (the base list) — see §7.
- **Never fabricate an unavailable metric** (retention/CTR/impressions/watch-time) — say plainly when data isn't available rather than estimating.
- **`state/performance_notes.json`'s `cycles[]` is append-only** — use the safe writer, never hand-edit past entries.
- **Never scout/produce a video for a day other than today** (§3).
- **Never rewrite an already-published video's live description/title** except to fix a real, current, owner-flagged bug (this has happened twice this session — always via a direct, verified API call, never blind).
- **Single end-of-firing git push** — commit locally after each item (cheap, gives crash resilience), but push exactly once at the very end of a firing. Pushing needs an explicit approval click in this environment; per-item pushes would require babysitting an otherwise-unattended run.
- **Background production sub-agents use `isolation: "worktree"`** (separate git worktree + branch) to avoid concurrent-write corruption of shared state files. Give them **relative paths from their own worktree root**, never the main checkout's absolute paths — a sub-agent given `/home/user/Idkk/...` paths will write directly into the main checkout and defeat the isolation. After a worktree agent finishes: verify independently (don't just trust its self-report — check the real YouTube API state), `git merge --ff-only` (or resolve simple append-only JSON-array conflicts by hand if the base diverged — this has happened when two worktree agents branch before the other's merge), then `git worktree remove --force` + `git branch -d`.
- **Never lower a gate to force a publish** — quarantine the candidate with a reason (`state/quarantine.json`) and move to the next candidate for that slot.

## 9. Outside the repo: scheduled triggers (Claude Code Remote Routines)

Two account-level Routines drive this pipeline daily (not stored in the repo — managed via the `claude-code-remote` MCP server's trigger tools):
- **"Daily YouTube content batch (@makeitmanifest)"** — `0 6 * * *` UTC, runs the Daily production cycle (§3).
- **"makeitmanifest-daily-analytics"** — `0 7 * * *` UTC, runs the Self-Improvement Protocol (§4).

Both fire into a persistent session (not a fresh one) because a fresh session per firing has no repo clone and no way to get one. **If you're asked to fix/update the pipeline's operating model, check whether a Routine's stored prompt needs updating too** — a Routine's prompt is a frozen copy of instructions at creation time; it does not automatically track changes to `agents/0_orchestrator.md`. This has already caused one real conflict this session (a stale Routine prompt describing the old Weekly-batch model after the switch to Daily production).

## 12. Practical notes for generating prompts against this repo

- Activate `.venv` for anything touching `youtube_auth`/`googleapiclient` (`source youtube-automation/.venv/bin/activate`). `generate_dashboard.py` needs PIL, which is only in system `python3`, not `.venv` — run it with plain `python3` instead.
- Real YouTube upload quota is a genuine constraint (~4 uploads/24h historically triggers `uploadLimitExceeded`) — be deliberate about triggering more than one day's worth of publishing in a test.
- This is a **live channel with a real, small, growing audience**. Any change that touches already-published content should default to "future videos only" unless the owner explicitly asks for a retroactive fix — and even then, verify via a live API call before and after, never assume a write succeeded.
